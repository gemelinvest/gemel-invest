# מדיניות אבטחת מידע — GEMEL INVEST CRM

**מסמך:** מדיניות אבטחת מידע ארגונית (Information Security Policy)
**גרסה:** 1.0  **תאריך:** 2026-10-02
**תחולת:** מערכת GEMEL INVEST CRM (SPA + Supabase) והמשתמשים המורשים בה
**בסיס רגולטורי:** חוק הגנת הפרטיות (התשמ״א-1981) ותקנותיו; תקנות העברת מידע למאגרים; חוק ניהול מאגרי מידע (התשפ״ב-2021); הוראות הפיקוח על ענף הביטוח.

---

## 1. מטרה ותחולה
מסמך זה מגדיר את דרישות האבטחה המחייבות למערכת CRM, למידע המוחזק בה (פרטי לקוחות, הצעות, לידים, מסמכים) ולמשתמשים הפנימיים. המסמך משלים את תוכנית האבטחה הטכנית ב-[`CRM_SECURITY_PROGRAM.md`](CRM_SECURITY_PROGRAM.md) ואת מפת התיקונים ב-[`CRM_REMEDIATION_ROADMAP.md`](CRM_REMEDIATION_ROADMAP.md).

## 2. עקרונות
1. **הרשאה מינימלית** — כל משתמש רואה רק את הנחוץ לתפקידו.
2. **הפרדת תפקידים** — אימות, הרשאה וביקורת מופרדים.
3. **אכיפה בשרת** — הרשאות נאכפות ב-DB (RLS) וב-Edge, לא רק ב-UI.
4. **תיעוד** — כל פעולה רגישה מתועדת וניתנת לביקורת.
5. **היערכות לאירוע** — קיים תהליך תגובה ודיווח (ראה [`INCIDENT_RESPONSE_PLAN.md`](INCIDENT_RESPONSE_PLAN.md)).

## 3. ניהול משתמשים וגישות
- **מתן גישה:** רק לאחר אישור מנהל ישיר, על בסיס צורך תפקיד מתועד; זהות ייחודית לכל משתמש (ללא שיתוף חשבונות).
- **סקירה תקופתית:** לפחות פעם ברבעון; השבה מיידית של משתמש שעזב; תיעוד שינויים.
- **תפקידים:** הרשאות לפי תפקיד (מטריצה בסעיף 5 של [`CRM_SECURITY_PROGRAM.md`](CRM_SECURITY_PROGRAM.md)). אכיפה ב-`app_metadata` + RLS, לא ב-`user_metadata`.

## 4. ניהול סיסמאות ואימות
- **דרישות:** אורך/מורכבות מינימליים; ללא ברירות מחדל חלשות (`1234`/`0000`/`1990` אסורות — Pב/R5); חובת החלפה בכניסה ראשונה ולאחר חשד לחשיפה; נעילה זמנית אחרי ניסיונות כושלים (rate limiting — שלב 12).
- **אחסון:** סודות אימות חייבים hashing/encryption, לא טקסט גלוי. חריגה נוכחית: `agents.pin` בטקסט גלוי — מסומן לתיקון. מפתח `service_role` אסור בקוד לקוח; סודות Edge ב-Supabase secrets.
- **MFA:** זמין ומומלץ למנהלים/תפעול; חובה למנהלים תיבחן (החלטה עסקית).

## 5. אבטחה לוגית ותפעולית
- **אכיפת הרשאות:** RLS דלוק על כל טבלאות הליבה; policies לפי תפקיד (Pד/Pה). Edge מאומתות לפי פעולה (Pא). Storage נעול לפי בעלות לקוח (Pו).
- **תקשורת:** TLS חובה; סודיות מול ספקים חיצוניים בהסכמים כתובים ובהצפנה במעבר.
- **תחנת קצה:** security headers (CSP, frame-ancestors, object-src, base-uri, referrer — שלב 12); עדכון וסריקת רכיבי צד שלישי (SCA).

## 6. ניהול סודות
- סודות בכספת (Supabase/GitHub secrets), לא בקוד או במאגר ציבורי. רוטציה לפי מדיניות ולאחר חשד לחשיפה. גישה לסודות מתועדת.

## 7. תיעוד וביקורת (Audit Trail)
- לוג פעילות (`gi_agent_activity_log`) תומך ב: כניסות, פעולות רגישות (קריאה/כתיבת לקוח, ייצוא, מחיקה), שינויי הרשאות.
- הלוגים מוגנים משינוי/מחיקה ע״י משתמש רגיל. שמירה לפי מדיניות retention (סעיף 8). סקירה תקופתית של הלוגים.

## 8. שמירת נתונים ומחיקה (Retention)
- הגדרת תקופות שמירה לפי סוג נתונים ודרישות חוק (ראה [`DATA_PROTECTION_AND_PRIVACY.md`](DATA_PROTECTION_AND_PRIVACY.md)).
- מחיקה רק באישור מורשה ובתיעוד; מחיקה בטוחה (לא שחזור אפשרי כשנדרש).
- ארכוב/השבתה לפני מחיקה לפי צורך עסקי/חוקי.

## 9. היערכות לאירוע אבטחה
- תהליך תגובה ודיווח מתועד ב-[`INCIDENT_RESPONSE_PLAN.md`](INCIDENT_RESPONSE_PLAN.md), כולל דיווח לרשם מאגרי מידע ולמפקח על הביטוח לפי החוק.

## 10. אחריות ואכיפה
- בעל המערכת אחראי לאכיפת המדיניות. הפרה עלולה להוביל להסרת גישה ולפעולה משמעתית.
- סקירה שנתית של המדיניות ועדכון לפי שינויים במערכת/בחוק.

## 11. מפת עמידה מול תקנות אבטחת מידע
| דרישה (תקנות הגנת הפרטיות) | מקום הטיפול |

| אבטחה לוגית (מניעת חדירה) | RLS + Edge auth + security headers (Pא/Pד/Pה/שלב 12) |
| ניהול סיסמאות | סעיף 4 + Pב/R5 + hashing |
| ניהול גישות | סעיף 3 + RLS לפי תפקיד |
| תיעוד | סעיף 7 + `gi_agent_activity_log` |
| היערכות לאירוע | סעיף 9 + [`INCIDENT_RESPONSE_PLAN.md`](INCIDENT_RESPONSE_PLAN.md) |
