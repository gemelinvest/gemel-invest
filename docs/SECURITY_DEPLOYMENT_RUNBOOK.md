## שלב 4 — Tier 1 לקראת מבדק הסייבר (תיקונים בטוחים, לא תלויים)

שלב זה מכסה תיקונים שמקשים על הבודקים **בלי לפגוע בתפקוד**. כל השינויים בקוד בלבד, למעט החלת SQL אחת (hashing PIN) שדורשת הפעלה ידנית.

### 4.0 — תנאי קדם חובה לפני מיזוג: ודא ש-PIN מנהל מוגדר ב-`app_meta`

שינוי בקוד מסיר את ברירת המחדל הקשיחה `1234` (backdoor) מכניסת מנהל. כתוצאה, כניסת מנהל תעבוד **רק** אם מוגדר `adminAuth` אמיתי ב-`app_meta`. **לפני המיזוג**, ודא ב-SQL Editor:

```sql
select meta->'adminAuth' as admin_auth from public.app_meta where key = 'global';
```

- אם חוזרת שורה עם `pin` לא-ריק ו-`active` אמיתי → תקין, אפשר למזוג.
- אם השורה ריקה / חסרה / `pin` ריק → **קבע תחילה PIN מנהל אמיתי** (בחר קוד חזק, לא 1234):

```sql
update public.app_meta
  set meta = jsonb_set(
    coalesce(meta, '{}'::jsonb),
    '{adminAuth}',
    '{"username":"מנהל מערכת","pin":"<PIN-חזק-שתבחר>","active":true}'::jsonb,
    true
  )
  where key = 'global';
```

> בחר PIN חזק (מומלץ 6 ספרות לפחות, לא רצף). שמור אותו במקום מאובטח ושתף אותו רק עם מנהלי המערכת.

### 4.1 — מזג את ה-PR של Tier 1

| **מה לשלוח לי** | אישור "מוזג Tier 1 + 4.0 בוצע + כניסות עובדות" |

### 4.2 — הפעלת hashing PIN (bcrypt) — אופציונלי אך מומלץ לפני המבדק

מעביד את `agents.pin` מטקסט-גלוי ל-hash bcrypt. **כפול בריצה (dual-run)** — אפס סיכון כניסה: כל עוד לא מולא `pin_hash`, ההשוואה חוזרת לטקסט-גלוי הקיים.

| | |
|---|---|
| **תנאי** | שלב 2 (#398) ממוזג וה-SQL שלו מופעל (יוצר את `gi_login_attempts` + `gi_security_settings`) |
| **פעולה א׳** | העתק את כל תוכן [`supabase-gi-pin-hashing.sql`](../supabase-gi-pin-hashing.sql) מ-`main` → SQL Editor → **Run**. זה מוסיף עמודת `pin_hash` ומגדיר מחדש את ה-RPC ל-dual-run. **שום נציג לא צריך PIN חדש.** |
| **פעולה ב׳ (backfill, אחרי א׳)** | מלא את ה-hash מתוך ה-PINs הגלויים הקיימים:<br>`update public.agents set pin_hash = extensions.crypt(coalesce(pin, ''), extensions.gen_salt('bf', 8)) where pin_hash is null and coalesce(pin, '') <> '';` |
| **בדיקה** | 1) כניסת נציג עם ה-PIN הקיים שלו — עובדת (כעת מול hash). 2) כניסת מנהל — עובדת. 3) ב-SQL Editor: `select id, (pin is not null) as has_cleartext, (pin_hash is not null) as has_hash from public.agents limit 5;` — רואים `has_hash = t`. |
| **כפתור חירום** | `update public.agents set pin_hash = null;` — חוזר מייד להשוואת טקסט-גלוי (העמודה `pin` נשארת שלמה). |
| **(מאוחר יותר, אופציונלי)** | אחרי וידוא שכל הנציגים נכנסים מול hash: `update public.agents set pin = null where pin_hash is not null;` — מאפס את הטקסט-גלוי. **רק אחרי וידוא!** |
| **מה לשלוח לי** | אישור "הפעלתי hashing + backfill + כניסות עובדות" |

> הערה: ברירת השרת `coalesce(ag.pin, '0000')` בנתיב הטקסט-גלוי נשארת לתאימות לאחור. לאחר backfill ואיפוס הטקסט-גלוי, ניתן להסיר את ברירת ה-`0000` הזו בשלב עתידי (Tier 2).

## שלב 5 — Tier 2 הכנה: הנפקת תעודות זהות (Auth) לסוכנים PIN-only

**תנאי הכרחי לפני סגירת גישת ה-anon והפעלת RLS (Pה).** כ-14 סוכנים פעילים עדיין נכנסים עם PIN בלבד (אין להם `auth_user_id`). אם נסגור את הגישה לפני שיקבלו תעודת זהות (JWT) — הם ינעלו החוצה. לכן: **קודם תעודות לכולם, רק אחר כך סגירת החור.**

המנגנון **כבר קיים** ב-`supabase/functions/gi-provision-agent-auth` (פעולות `preview_missing` / `provision_missing`). ההקצאה נעשית עם סיסמה אקראית חזקה שהסוכן לעולם לא מקליד; הכניסה נשארת עם ה-PIN הרגיל. אין כפיית אימות דו-שלבי. **אין שינוי לסוכנים ביומיום.**

### 5.1 — סקריפט עזר

הכנתי `scripts/provision-auth.mjs` שמפעיל את המנגנון הקיים דרך הטרמינל, עם אימות מנהל מול השרת.

### 5.2 — צעדים

| | |
|---|---|
| **תנאי** | שלב 4.1 ממוזג (PIN מנהל מוגדר ופעיל) |
| **פעולה א׳ — תצוגה מקדימה (ללא שינוי)** | בטרמינל (עם פרטי המנהל שהגדרת ב-4.0):<br>`GI_ADMIN_USER="מנהל מערכת" GI_ADMIN_PIN="<pin>" node scripts/provision-auth.mjs`<br>מדפיס את רשימת הסוכנים שיוקצו להם תעודות (ה-14) ואת האימייל המוצע. **שום דבר לא נכתב.** |
| **פעולה ב׳ — הקצאה (כותב)** | לאחר וידוא הרשימה:<br>`GI_ADMIN_USER="מנהל מערכת" GI_ADMIN_PIN="<pin>" node scripts/provision-auth.mjs --provision`<br>יוצר חשבונות Auth ומקשר `auth_user_id`. הסוכנים לא צריכים לעשות דבר. |
| **בדיקה** | 1) הסקריפט מדפיס `created = N`, `skipped = 0`. 2) בקש מכל סוכן שהוקצה להיכנס עם ה-PIN הרגיל שלו — עובד. 3) הרץ שוב preview (בלי `--provision`) — `count = 0`. |
| **כפתור חירום** | אם משהו השתבש: הרץ ב-SQL Editor `update public.agents set auth_user_id = null where id in ('<id1>','<id2>');` לביטול הקישור (חשבונות ה-Auth שנוצרו לא מזיקים — הם לא משמשים לכניסה בלי הקישור). |
| **מה לשלוח לי** | אישור "provision הושלם, count=0 ב-preview, כל הסוכנים נכנסים" |

> **רק כש-`count = 0` ב-preview** — כל הסוכנים הפעילים מחזיקים תעודת זהות — אפשר לעבור לסגירת גישת ה-anon והפעלת RLS (Tier 2, Pה). עד אז **לא** לסגור את הגישה.
